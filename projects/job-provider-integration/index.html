Job-provider integration

This integration service maps different job-provider payloads into a common model. It demonstrates the work at an API boundary: normalizing data, preserving related records, and offering a consistent query surface.

Normalize before the rest of the application depends on it

Provider formats differ in fields and structure. The service maps those inputs into a shared representation, allowing application queries to work against the normalized model rather than repeating provider-specific decisions everywhere.

The code includes mappings, entities, migrations, and provider-specific integration logic. Focused tests exercise normalization behavior, which is where small differences in input can otherwise produce inconsistent records.

Use a transaction at the job boundary

Related upserts are coordinated per job. That gives the write path a clear unit of work and avoids describing a whole provider import as one indistinguishable operation.

The API also supports filtering and pagination. The repository documents limitations, including work still needed around bounded batch concurrency. It is a concrete integration implementation, not a claim of verified production scale.

Make the repository useful to a reviewer

The public source provides a path from provider payload to mapping, persistence, and API query. That is the most useful way to read the project: follow one record and inspect how its relationships are represented.

Project notes

Public integration project. Provider access and a database are needed to run it; bounded batch concurrency remains follow-up work.
