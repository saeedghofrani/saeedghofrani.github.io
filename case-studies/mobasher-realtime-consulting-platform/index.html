Mobasher: microservices behind messaging and consultation

Mobasher combines consulting and learning with communication. I developed backend services in a NestJS microservice architecture, integrated communication workflows with the Angular application, and worked on SQL retrieval paths for frequently used screens.

My role
Backend Engineer (Freelance) · 2023–2025
Project scope
Client-owned production platform · private source

On this page

Result and scope

500+ concurrent production users with observed messaging latency of 100–150 ms.

A consultation is more than a call

The product brings together provider information, reservations, educational workflows, and live communication. Messaging and a voice/video session sit inside that larger application context. A user may move from choosing a provider to arranging a session and then communicating, so those transitions need usable backend contracts.

The local client workspace contains separate application and broker structures as well as provider and reservation services. That supports a description of a service-based product, rather than presenting the work as one isolated chat endpoint. My confirmed contribution is backend and communication integration; I do not claim ownership of every application in the client workspace.

Different communication tools for different jobs

WebRTC handles the media side of voice and video sessions. Socket.IO supports event-driven interaction with the application, and RabbitMQ participates in backend communication workflows. These tools solve different problems, even when a user experiences them as one session.

I integrated those workflows with Angular and developed the associated NestJS services. The engineering work involves coordinating application state around communication: the session is not only a media stream, and the existence of a socket connection is not itself proof that a consultation has completed.

Data retrieval still matters in a real-time product

I improved SQL stored procedures and retrieval paths for frequently used screens. A real-time feature can be responsive while the surrounding provider, reservation, or history screen remains slow. Both sides affect the experience.

The database work belongs in the same story as the communication layer. It demonstrates that my contribution included the ordinary data paths users rely on before and after a session, alongside the more visible messaging and media features.

Keeping production and load-test results separate

The confirmed production observation was more than 500 concurrent users, with messaging latency between 100 and 150 milliseconds. A separate load test observed approximately 30 milliseconds. These are different contexts and should not be combined into one stronger-looking result.

The latency figure refers to messaging. It is not an audio/video latency measurement, a percentile, or a guarantee for every network. Test hardware, sampling details, and load-test concurrency are not asserted. This keeps the result useful to a technical reader without overstating what was measured.

The contribution in context

The project gave me experience connecting microservices, database-backed workflows, and user-facing real-time behavior in a freelance engagement. The strongest evidence is the combination of the implemented services, the integration scope, and the confirmed production observation.

The public description stays at that level because the underlying client code and user data are private. A technical conversation can still examine how the components interact and how the observed result was measured without publishing those materials.

Evidence and boundaries

Production concurrency and messaging latency are explicitly owner-confirmed. The separate load-test observation is retained with its limits. A current public application URL is not inferred from private configuration.
