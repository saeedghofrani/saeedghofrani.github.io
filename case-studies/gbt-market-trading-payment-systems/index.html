GBT Market: wallets, trading, and a separate chart pipeline

GBT Market is a gold and cryptocurrency trading platform. My ongoing freelance work covers backend services for orders, portfolios, wallets, payments, live market data, support, and administrative reporting. The separate chart applications are also deployed and used in production.

Result and scope

Financial operations can overlap

A trading application cannot assume that requests arrive once, in a convenient order. Two wallet operations can reach the backend together. A payment callback can be retried. An administrator may investigate an operation while related records are still changing.

My work includes atomic balance updates, concurrency protection, and idempotency safeguards. These address specific failure modes: spending the same available balance twice, applying a repeated operation more than once, or creating duplicate transaction-log effects. The important result is preserving the meaning of a financial operation across those paths.

This is not a claim that one database transaction covers every external payment provider. The integration boundary matters: an external callback, an internal balance update, and an audit record have different failure conditions. The implementation and regression work have to account for those boundaries.

Orders, payments, and support are connected

The backend includes trading and melted-gold markets, portfolios, order settings, wallet transfers, deposits and withdrawals, payment integrations, commissions, and referrals. I contribute across those services rather than treating each as an unrelated endpoint.

Administrative reporting and support are part of that work. A financial event needs to remain understandable when it is exported, searched, or investigated in a ticket. Recent delivery included localized report fields, ticket administration, reporting filters, and compatibility for historical data. Some presentation fields can be calculated when a response is built, allowing old records to benefit without a database backfill.

Separating chart updates from order execution

The local project family includes dedicated NestJS chart applications. Their purpose is to process price events, maintain current price data in Redis, update chart history in MongoDB, and prepare events for client broadcasts. They support multiple timeframes, from minute-level candles through daily history.

The chart application explicitly separates this work from order processing such as margin closure, take-profit/stop-loss handling, and limit orders. That is a useful boundary: presenting a price history and executing a financial action are different responsibilities, even when both react to the same market information.

The chart-data service also contains history retrieval, cache initialization, and cleanup responsibilities. Persisted history and fast current reads have different access patterns, so the system uses MongoDB and Redis for distinct jobs. Both chart applications were confirmed as deployed production work; no independent throughput or latency benchmark is claimed here.

Real-time delivery has more than one stage

Socket.IO delivers updates to connected clients. Redis pub/sub supports communication and fan-out across processes, while Bull handles background work. The source also contains scheduled jobs and production process configuration.

A price can be correct in storage while the screen is stale, or visible on the screen before another downstream operation has finished. Describing the system as simply “real time” hides those distinctions. I work on the service boundaries and update paths so each consumer receives the data it needs without confusing a notification with the authoritative financial record.

Reporting and production delivery

My contributions include MongoDB query and report improvements, market-cache isolation, notification boundaries, and deployment support with Docker and Nginx. The work also involves Jest/Supertest regression tests and investigation of production issues.

Source history and the project chat provide evidence of focused fixes and reviewed deliveries. I keep those engineering results scoped to their actual change; I do not turn a single report optimization into an unsupported platform-wide speed claim. The same discipline applies to production checks: passing a focused test does not mean every trading path has been certified.

What I would show in a technical discussion

A useful walkthrough follows one wallet operation and one price update. For the wallet operation, I would explain the balance condition, duplicate handling, and the associated record. For the price update, I would trace event ingestion, current-state caching, candle history, and client delivery.

That pair of examples shows why the platform needs both consistency and responsiveness. A fast broadcast does not prove a correct ledger, and a correct ledger does not make a delayed chart acceptable. They have to be designed and reviewed as related, distinct paths.

Evidence and boundaries

Ongoing engagement and production use of both chart applications are owner-confirmed. Code and chat history support the technical scope. GBT Market and Keyvangold are separate engagements; this page does not assign GBT-specific implementations to Keyvangold.
